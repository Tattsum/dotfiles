# Plan First — 着手前ワークフロー

非自明な実装・調査・設計に着手する前に必ず通す標準手順。**車輪の再開発をしない／セキュアに技術選定する／合意してから動く**を強制する。実装で終わってもよいし、**調査・設計の洗い出しで完結してもよい**（終端は Phase 5 参照）。

## Why this matters

いきなりコードを書くと、(1) 既存資産や OSS で済む車輪の再開発、(2) サプライチェーンリスクを抱えた依存の安易な採用、(3) 設計の手戻り、が起きる。調査と合意を実装の前段に置くことで、これらを着手前に潰す。`CLAUDE.md`「実装着手前ワークフロー（必須）」の実体がこのスキル。

## オーケストレーション方針

このスキルはメイン（オーケストレーター）がフェーズを管理し、**重く独立した調査・検証はサブエージェントに隔離**する。サブエージェントには要約だけ返させ、メインのコンテキストを軽く保つ。ユーザーとの対話（合意形成）と最終判断はメインに残す。各フェーズの担当を以下に明示する。

| Phase | 担当 | サブエージェントに隔離する理由 |
|------|------|------|
| 0 発動判定 | メイン | 軽量な判断のみ |
| 1 並列調査 | サブエージェント ×2（ローカル `Explore` / OSS Web 調査） | 大量のコード走査・Web 取得をメインから隔離 |
| 2 セキュア技術選定 | サブエージェント ×1（新規依存ありのときのみ） | スキャナ実行・各候補の調査をメインから隔離 |
| 3 敵対的検証 | サブエージェント ×1（必須条件のときのみ） | 独立した second opinion を別コンテキストで得る |
| 4 /grill-me 合意 | メイン（`/grill-me` に委譲） | ユーザーとの対話そのもの |
| 5 合意サマリ→実装 or 調査終端 | メイン | 意思決定と着手（または調査・設計提示で終了） |

各フェーズではサブエージェントの戻り値（要約）だけを受け取り、メインで統合する。生のコード・履歴・Web 全文はメインに持ち込まない。

## Phase 0 — 発動判定（担当: メイン）

以下のいずれかに当てはまるか確認する。**1つも当てはまらないなら、このスキルは使わず通常どおり実装してよい。**

- **新規依存を足す**（Go module / npm / OSS ライブラリ等を新たに導入する）
- **設計判断を伴う**（アーキテクチャ・API/スキーマ・データモデル・抽象化の選択がある）
- **後戻りコストが高い**（マイグレーション・公開 API 変更・広範囲に影響する変更）

対象外（このスキルを使わない）: バグ修正・誤字・リネーム・フォーマット・設定値変更など、設計判断を伴わない機械的変更。

判定結果を一言で宣言してから次へ進む（例: `→ 発動（新規依存 + 設計判断）` / `→ 非該当のため通常実装`）。

**終端は問わない**: 設計判断を伴う調査・検討・列挙タスク（「検討して」「洗い出して」「列挙して」系）も対象に含む。コードに至らず調査・設計提示で完結してよい（Phase 5 参照）。「実装しないから対象外」ではない。

## Phase 1 — 並列調査（担当: サブエージェント ×2）

車輪の再開発を防ぐ調査。`Agent` で **2 系統を並列起動**する（1 メッセージで両方を発射）。結果は context を汚さないよう要約で受け取る。

1. **ローカル既存資産の調査**（`Explore` 推奨）: このリポジトリ・社内資産に、流用できる実装・ユーティリティ・パターンが既にないか。「同等機能が既にある」「一部流用できる」「無い」を根拠付きで報告させる。
2. **OSS / 標準パターンの調査**（`WebSearch`/`WebFetch` 可）: 同種の課題を解く OSS・標準ライブラリ・確立された設計パターン。設計思想（何を抽象化し何をしないか）を抽出させる。**OSS の思想は積極的に取り込む。**

統合して「流用するもの / 新規に書くもの / 取り込む設計思想」を一覧化する。

## Phase 2 — セキュアな技術選定ゲート（担当: サブエージェント ×1）

新規依存を採用する場合のみ実施（既存依存だけで済むなら skip し、その旨を宣言する）。

`Agent` を 1 体起動し、Phase 1 で挙がった依存候補について下記の判断軸調査とスキャナ実行を行わせ、**候補ごとの採否と根拠だけを要約で**返させる。スキャナの生ログや調査の全文はメインに持ち込まない。

**判断軸チェックリスト**（各候補について）:

- メンテ状況（最終コミット・リリース頻度・issue 応答）
- 採用実績（star / ダウンロード / 既知の利用者）
- 既知の脆弱性（CVE）
- ライセンス（プロジェクトと整合するか）
- タイポスクワット（正規パッケージ名か、似た名前の偽物でないか）
- バージョンのピン留め（`==` / 厳密指定ができるか）

**脆弱性スキャナの実行**（対象リポジトリに導入済みのものを使う）:

- Go: `govulncheck ./...`
- 任意言語: `osv-scanner scan .`（OSV.dev 準拠）
- npm: `npm audit`

未導入の場合はインストールを強制せず、**チェックリストのみで判断**し「スキャナ未実行（未導入）」と明示する。スキャナを新たに入れる判断自体も新規依存なので、このゲートを適用する。

## Phase 3 — 敵対的検証（担当: サブエージェント ×1）

second opinion。**新規依存導入 or 後戻りコストが高い判断のときは必須。** それ以外は任意。

別 `Agent` に、Phase 1–2 の結論を渡して反証させる:

- 「本当に車輪の再開発でないか（既存資産/標準ライブラリで足りないか）」
- 「選んだ OSS / 設計は本当に最適か。より枯れた・より安全な代替はないか」
- 「探し方が浅いだけで見落としていないか」

反証で覆る点があれば Phase 1–2 に戻る。

## Phase 4 — /grill-me で合意形成（担当: メイン）

調査・選定・検証の結論を素案としてまとめ、**既存の `/grill-me` を `Skill` 経由で起動**して設計決定を一問一答で詰める。`grill-me` のルール（一問一答・推奨を必ず添える・ローカル調査優先・ユーザー判断が必要な問いのみ）に従う。ユーザーが「進めて」等の実行指示を出すまで実装に着手しない。

## Phase 5 — 合意サマリ → 実装 or 調査・設計終端（担当: メイン）

合意内容を一覧（決定事項 → 結論の表）で提示する。ここで**2 通りの終端**のいずれかを取る。どちらも正規の終わり方で、実装終端が上位ではない。

- **実装終端**: 合意した設計で実装に着手する。成果物はコードなので durable。実装着手後、コミット/PR が必要になったら `dotfiles-commit-push` / `dotfiles-pr-create` の規約に従う（このスキルはコミットしない）。
- **調査・設計終端**: 実装に進まず、洗い出し・設計案・技術選定結果の提示で完結する（「検討したい」「列挙したい」系タスク）。これは誤用ではなく正規の終端。

**plan doc のファイル化はデフォルト不要**（会話のサマリ表で足りる／YAGNI）。「規模が大きい・後で参照が要る」ときのみ 1 枚だけファイル化する。その際の規約:

- **置き場はセッションの scratchpad（システムが指定する一時ディレクトリ）に決め打ち**する。リポジトリ（`docs/` 等）を汚さない。参照が終われば破棄してよい中間成果物として扱う。
- **最小テンプレ**に留める: `決定事項 → 結論` の表 ＋ 調査で却下した代替案（Why not）のみ。順方向の背景説明（Why）や実装手順（How）は書かない（四分割原則: plan doc は合意記録であってコード・コミットログの代替ではない）。

## Output format

- Phase 0 の判定を一言で宣言
- Phase 1–3 の調査・選定・検証結果を簡潔に統合
- Phase 4 は `/grill-me` に委譲
- Phase 5 で合意サマリ表を提示し、実装 or 調査・設計提示で終端する
