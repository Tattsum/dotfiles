## 目的

PHP / Laravel のコード差分を **複数観点で漏れなくレビュー**する。コードの修正は行わず、指摘リストの報告に徹する。

## 方針

- 比較元ブランチ（デフォルト `origin/master`、なければ `origin/main`）との差分をレビュー対象にする
- diff の `@@` 行番号ではなく、**実ファイルを読んだ上での行番号**で指摘する
- 観点ごとに独立して見て、最後に統合した指摘リストにまとめる
- 言語仕様（[PHP Manual](https://www.php.net/manual/)）・[Laravel Docs](https://laravel.com/docs)・[PSR-12](https://www.php-fig.org/psr/psr-12/) を根拠の正本とする
- スタイル系のルール（変数名の case など）は **そのリポジトリ既存の規約に合わせる**。リポジトリ規約がない一般原則のみを指摘する

## ワークフロー

1. `git diff <base>...HEAD --stat` で対象を確認（差分がなければ「対象なし」と報告して終了）
2. 変更された `*.php` と `database/migrations/` のファイルを特定する
3. 各ファイルを読み、正確な行番号を把握する
4. 下記の観点ごとにレビューする
5. 結果を統合し、重要度別に出力する

## レビュー観点

### コード規約・可読性
- 命名はリポジトリ既存の規約に一貫しているか。`data` / `info` のような情報量のない汎用語を避けているか
- enum 的に扱う定数で網羅的に分岐する場合は `switch` を使い、`default` で未知値を弾いているか
- `empty()` で必須値の有無を判定していないか（`'0'` / `0` / `false` を「空」と誤判定する。null 判定は `is_null()` / `??` を使う）
- 一時的な作業メモや漠然とした TODO を残していないか（master にマージして問題ない内容のみ）

### 型安全性・設計
- 引数は ID 文字列ではなくモデル/エンティティのインスタンスを受け取り、存在保証と補完を効かせているか
- PHPDoc は `mixed` を避け具体型を指定しているか。DB 由来の型は IDE Helper 生成の型定義（`_ide_helper_models.php` 等）に合わせているか
- 既存インスタンスを変更するより、新インスタンスを生成するイミュータブルな実装を優先しているか
- **YAGNI**: 現時点で使われないメソッド・プロパティ・クラス・引数を追加していないか

### Laravel 責務分離
- Controller が肥大化していないか（UseCase / Service への切り出し）。Eloquent Model にロジックを詰め込みすぎていないか
- 入力検証は FormRequest に集約されているか。トランザクション境界（`DB::transaction()`）は適切か
- クラス内定義順（定数 → プロパティ → コンストラクタ → メソッド）、`use` でのインポート、全メソッドの戻り値型宣言

### DB 設計（マイグレーション）
- 外部キー制約は原則付けない（暗黙の共有ロックによる deadlock 回避。整合性はアプリ層で担保）
- 主キーは整数型（BIGINT / INT）の Auto Increment な `id`（UUID は避ける）。パーティションテーブルのみ複合主キーを許容
- インデックス/制約名はフレームワークの自動命名に任せる（64 文字制限時のみ手動短縮）
- 全マイグレーションに `down()` を実装する。`nullable(false)` 化を戻す `down()` は NULL データのクリーニング手順も書く
- 文字コードは `utf8mb4` + 適切な COLLATE（`utf8` / `utf8mb3` は不可）。時刻は `DATETIME`、`created_at` / `updated_at` は `CURRENT_TIMESTAMP` の定型
- 既知の値が必ず入るカラムは `NOT NULL` + デフォルト。IN 句に空配列を渡さないガード

### テスト
- テスト名は `test_{対象関数}_{ケース}` 形式で意図が読み取れるか。可読性のため `@testdox` 等の説明アノテーションを活用しているか
- Arrange / Act / Assert を視覚的に分離し、複数項目は `$expected` 配列にまとめて 1 回で検証しているか
- プリミティブ/同一インスタンスは `assertSame()`、配列/オブジェクトの構造比較は `assertEquals()`
- 内部実装ではなく **振る舞い（戻り値・DB 状態変化・外部 API 呼び出し）** を検証しているか（「特定メソッドが呼ばれたか」等に依存しない）
- モックは外部依存（外部 API / ファイル / メール / 決済）のみ。同一アプリ内のサービス・Eloquent・内部ロジックはモックしない
- 時刻は `Carbon::setTestNow()` 等で固定し、`now()` を直接使わない
- DB テストは `DatabaseTransactions` を優先（`RefreshDatabase` は避ける）。書き込みは `assertDatabaseHas` で検証
- 単体テストに実 API / 実 DB を叩く分岐（`if (env(...))` 等）を入れない。実 API テストは別ディレクトリ・別クラスに分離

### セキュリティ
- SQL インジェクション: 生クエリ / `DB::raw` / 文字列連結を避け、バインドを使っているか
- マスアサインメント: `$fillable` / `$guarded` が適切か
- 認可漏れ: マルチテナントで他テナントのデータが混ざらないか（テナント ID スコープの徹底）
- 機微情報（トークン・PII）をログ・例外・レスポンスに出していないか
- XSS: Blade の `{!! !!}` やフロントへ渡す HTML 文字列のエスケープ

## 出力フォーマット

重要度別に、`[ファイルパス:行番号]` 付きで指摘する。

```
## 🔴 Must（必ず修正）
- [path:line] 問題 → 修正案

## 🟡 Should（できれば修正）
- [path:line] 問題 → 修正案

## 🟢 Nice to have（提案）
- [path:line] 提案
```

各観点で指摘がなければ「該当なし」と明記する。
