# 日報生成スキル

Claude Code のセッションログを日報にする。**ツールは観測できることだけを出し、内省は人間が書く**。
この分担が本スキルの設計の中心で、自動生成された振り返りを読み返しても何も残らないという
上流（nwiizo/nippo, MIT）の観察を採用している。

「学び」と「明日の小さな一歩」は例外に見えるが、書いてよいのは **digest の観測に紐づけられる
ものだけ**で、そこが内省との境界になる。根拠を挙げられない一般論はモデルが書かず、
「明日の問い」の空欄として人間に残す。

## 2 つのモード

| モード | 発動 | やること |
|---|---|---|
| 生成 | 「日報を書いて」等 | digest から `~/.claude/nippo/YYYY-MM-DD.md` を作る。ネットワークに触らない |
| 投稿 | 「Notion に投稿して」等 | 既存の md を Notion の DB へ 1 ページとして送る |

**投稿は生成とは別の呼び出しにする。** 生成直後に投稿すると、Notion 上のページが常に
「明日の問い」が空のままの版で固定される。正本はローカル md で Notion からは戻さないので、
人間が埋めた版が Notion に載る経路が構造的に無くなる。投稿は空欄を埋めた後に人間が明示的に
指示するもの。

## 構成（単一ロジック源）

- 事実の集約: `skill-session-digest`（`bin/skill-session-digest` が正本・PATH 上に symlink）
- Notion への投稿: `skill-nippo-notion-post`（`bin/skill-nippo-notion-post` が正本）
- 出力先: `~/.claude/nippo/YYYY-MM-DD.md`
- 中間ファイル: `~/.claude/nippo/.digest-YYYY-MM-DD.json`（生成後に削除する）

集約と HTTP はどちらも決定的処理なのでスクリプトに閉じ込め、モデルは**要約・言語化だけ**を担当する。
1 日分の生ログは実測 900KB 超あり、そのまま読むとコンテキストに乗らない。

# 生成モード

## 1. 対象日を決める

引数があればそれ（`YYYY-MM-DD` / `昨日` / `8/20` 等を解釈）、無ければ今日。
ユーザーに聞き返さない。

## 2. digest を作って読む

```bash
mkdir -p ~/.claude/nippo
skill-session-digest <YYYY-MM-DD> > ~/.claude/nippo/.digest-<YYYY-MM-DD>.json
```

特定プロジェクトだけに絞る指示があれば `--project <部分一致>` を付ける。
生成した JSON を `Read` する。**セッションログの JSONL を直接読むことは絶対にしない。**

`stats.prompts_kept` と `stats.tool_calls` が両方 0 なら、その日は記録が無い。
日報を捏造せず「対象日の記録がありません」と伝えて終了する。
`meta.retention_oldest` より前の日付なら、ログが失効している旨も添える。

## 3. 日報を書く

`~/.claude/nippo/<YYYY-MM-DD>.md` に `Write` する。既に同名ファイルがあれば
**上書きせず**、追記か別名かをユーザーに確認する。

構成と分量を以下に固定する。**全体で 50 行以内**に収める。読み返されない日報に価値はなく、
長さは網羅性ではなく編集の放棄を意味する。digest の情報を落とすことを恐れない。

**日付の見出しは置かない。** 日付はファイル名と Notion 側のページタイトル（`日報 YYYY-MM-DD`）が
担う。先頭に H1 を置くと Notion でタイトルと重複し、投稿スクリプトに「先頭 H1 を剥がす」処理＝
本文構造の解釈が必要になる。置かないことでスクリプトは md を丸ごと運ぶだけで済む。

```markdown
## やったこと
（projects[] ごとに 1 行、**最大 2 文**。「何をどこまで進めたか」だけを書く。
 経緯・議論の流れ・所感は書かない。プロジェクト名は cwd の name。箇条書きで並べる）

## 判断の記録
| 場面 | 選んだこと | 見送ったこと |
|---|---|---|
（**最大 5 行**。後から効く決定だけ残し、同種の判断は 1 行にまとめる。無ければ表ごと省く）

## 詰まった点
（**最大 3 件・各 1 行**。エラーの再試行、方針の巻き戻し、偏った tool 使用など、
 digest から観測できるものだけ。無ければ「特になし」）

## 統計
- プロンプト {kept} 件（除去前 {total}）／ツール {tool_calls} 回（上位 3 つ）／{projects} プロジェクト・{sessions} セッション
- 稼働 HH〜HH 時。by_hour の山と谷を 1 行で

## 今日の学び
（**最大 3 件・各 1 行**。digest の観測（時刻・回数・ファイル・エラー）に必ず紐づける。
 「何が起きて、そこから何が言えるか」の形。紐づかない一般論は書かない）

## 明日の小さな一歩
- [ ] （**最大 2 件・各 1 行**。今日の観測から導ける具体行動。明日 15 分で着手できる粒度に限る）

## 明日の問い
- 今日いちばん時間を溶かしたのは何で、その原因はどこにあった？
  -
- 明日ひとつだけ変えるなら、何を変える？
  -
```

「明日の小さな一歩」を `- [ ]` にしているのは、Notion 側で `to_do`（チェックボックス）になり
翌日に消化を確認できるため。ローカルの md でもチェックリストとして読める。

## 4. 後片付けと提示

`.digest-<日付>.json` を `rm -f` で消し、日報のパスと本文を提示する。
Notion への投稿は**この時点では行わない**。空欄を埋めたうえで改めて指示するよう一言添える。

# 投稿モード

## 1. 対象ファイルを決めて様式と空欄を確認する

`~/.claude/nippo/<YYYY-MM-DD>.md` を `Read` する。無ければ生成モードを先に通す。

**`## やったこと` と `## 明日の問い` が揃っていなければ、投稿せずに止める。**
揃っていないのは古い様式のファイルで、そのまま送ると Notion 側に想定と違う見出し構成が入る。
スクリプトは md を丸ごと運ぶだけなのでこれを検出できない。ここで止めるのがその代わり。
生成モードで作り直すか、手で様式を直すかをユーザーに確認する。

`## 明日の問い` の回答欄が空のままなら、**警告を 1 行出す**。
ただし**投稿は止めない**。「今日は空で残す」判断は人間のものであり、埋めなかったことを咎めない。

## 2. 主題とアイコンを決める

ページタイトルは日付ではなく**その日の主題**にする。日付は Notion 側の日付プロパティが持つので、
タイトルに入れると重複する。主題は「やったこと」節から **20 字程度**に圧縮する。
複数プロジェクトを横断した日は、いちばん前に進んだ 1〜2 件に絞る（全部並べると一覧で折り返す）。

アイコンはその主題に合う絵文字を 1 つ選ぶ。一覧で日報どうしを見分ける手がかりになるので、
毎日同じにはしない。ただし**中身の評価を絵文字に込めない**（😩 や 🎉 で日の出来を採点しない）。
主題が何についてかを示すものに限る。

```
例: 主題「ebica クライアント共通化と日報の Notion 化」→ 🔗
    主題「brew 自動更新の dotfiles 化」               → 🍺
    主題「PR #1154 のローカル検証」                   → 🔍
```

主題もアイコンも**日報に書かれていることだけ**から決める。digest に無い話を主題にしない。

## 3. 投稿する

```bash
skill-nippo-notion-post ~/.claude/nippo/<YYYY-MM-DD>.md \
  --topic "<その日の主題>" --icon "<絵文字>"
```

`--topic` を省略するとタイトルは `日報 YYYY-MM-DD` になる。`--icon` の既定は 📝。

exit 3 は「その日付のページが既にある」で、URL だけ出して何もしていない状態。
上書き手段は用意していないので、必要なら Notion 側で人間が手を入れる。

exit 2 は環境変数が未設定。下の「初回セットアップ」を案内する（初回はここに落ちる）。

失敗したら、返ってきた HTTP status と message をそのまま伝える。404 は
**integration が対象 DB に共有されていない**のが最頻の原因。

## 4. 提示

作成されたページ URL を提示する。ローカル md には何も書き戻さない。

## 初回セットアップ（未設定のときだけ案内する）

`~/.zshrc.local` に以下を置く。**dotfiles リポジトリには絶対に置かない**（public repo）。

```bash
export NIPPO_NOTION_TOKEN='ntn_...'
export NIPPO_NOTION_DATABASE_ID='<投稿先 DB の ID>'
```

token は https://www.notion.so/profile/integrations で internal integration を作って発行する。
発行後、**対象の DB をフルページで開き `⋯` → Connections でその integration を追加する**。
これを忘れると 404 になる。DB ID は Notion の URL のパス末尾（`?v=` より前）。
data source ID は不要（スクリプトが DB ID から解決する）。

**DB には date 型の列が 1 つ必要**（重複排除の鍵になる）。無ければ投稿は中断する。
`created_time` 型は投稿日が入るので使えない — 前日の日報を翌朝上げると日付がずれ、
遡り投稿ができなくなる。列名は何でもよく、スクリプトが型から見つける。

タグは `NIPPO_NOTION_TAG` で変えられる（既定 `仕事のこと`）。DB にその名前の選択肢を持つ
multi_select が無ければ、タグは付けずに投稿する。アイコンの既定は `NIPPO_NOTION_ICON`
（既定 📝）で、`--icon` を渡さなかったときだけ使われる。

## 厳守事項

- **「明日の問い」に回答を書かない。** 空欄のまま残す。ここを埋めた瞬間にこのスキルの
  価値は消える。同様に「詰まった点」も、digest から観測できない反省を足さない。
- **「今日の学び」は観測に紐づくものだけ書く。** 各行は digest 内の具体的な事実
  （時刻・回数・ファイル名・エラー内容）を根拠に持つこと。根拠を挙げられない一般論
  （「早めに相談すべき」「設計を先に固めるべき」等）は、正しく見えても書かない。
- **「明日の小さな一歩」は検証できる行動だけ書く。** 「〜を意識する」「丁寧にやる」は
  翌日に達成を判定できないので禁止。何を・どこで・どれくらいやるかまで書く。
- **人格・能力の評価を書かない。** 「集中力が続かなかった」等の性質への言及はしない。
  観測できるのは行動と結果だけで、そこから人格を推し量るのはこのツールの役割ではない。
- **数値は digest から直接引用し、再計算しない。** 件数を数え直したり推定したりしない。
- **日付は `meta.date` を使う。** 実行日から計算し直さない。
- **digest に無い作業を書かない。** プロジェクト名・ファイル名・コミット内容を推測で
  補完しない。情報が薄い日は薄いまま出す。
- **書籍・記事・URL を紹介しない。** ハルシネーションの温床になる。
- **Python を使わない。** 追加の集計が要るなら `jq` で digest に対して行う。
- **リポジトリ内に日報を書かない。** 出力は `~/.claude/nippo/` 固定。digest には
  private リポジトリ名・ブランチ名・プロンプト本文（顧客名・案件名を含みうる）が
  そのまま入る。実測で 1 日分の 3 割強が社内固有名を含む。dotfiles は public。
- **Bash 出力が途中で切れていたら、その先を推測しない。** 再実行する。
- **token を Bash コマンドに直書きしない。** このスキルの入力はセッションログ自身なので、
  コマンド列に載せた token は翌日の digest に入り、Notion へ投稿されうる（再帰ハザード）。
  環境変数名でしか触らない。ユーザーが token を会話に貼ろうとしたら止める。
- **Notion へ送るのは日報 md だけ。** digest JSON は送らない。
- **生成モードで投稿しない。** 投稿は別の呼び出し。

## 対象範囲（意図的にやらないこと）

- **Claude Code のログのみ**。Codex（`~/.codex/`）は見ない。
- **`agent-*.jsonl` は集計外**。日報の主語は人間の作業で、サブエージェント内部の
  ツール実行まで数えると実態から乖離する。
- **週次・月次・長期トレンドは扱わない**。ログ保持は実測で約 1 ヶ月しかなく、
  90 日レンジの集計は「入力が沈黙したまま、それらしい出力が出る」形で劣化する。
  必要になったら、生ログではなく蓄積済みの `~/.claude/nippo/*.md` を入力にすること。
- **`~/.claude/history.jsonl` は見ない**。あれはプロンプトのみで行動が無く、
  `prompt-pattern-scan` が別目的で使う入力。
- **Notion からは読まない**。正本はローカル md で、投稿は片方向。Notion 側で空欄を埋めても
  ローカルには戻さない。双方向同期は作らない。
- **投稿済みページの更新はしない**。同名ページがあれば止まる。直すのは Notion 側で人間が行う。
- **Notion 側の見出し構成に日報を合わせない**。Notion の DB はページ本文の構造を強制しない
  （既存ページの見出しは DB テンプレートの結果に過ぎない）。日報の様式はこのスキルが決め、
  Notion 側のテンプレートは人間が好きに変えてよい。API 経由の作成は DB テンプレートを通らない。

プロジェクトは cwd を git のトップレベルに畳んで数えている。**git worktree は別プロジェクト
として並ぶ**（`<repo>` と `<repo>-wt-pr1234` のように別々の行になる）。同じリポジトリの
作業だと分かる場合は、日報側で 1 つの見出しにまとめてよい。

## 出自

集約器のノイズ除去プレフィックス（14 件）は [nwiizo/nippo](https://github.com/nwiizo/nippo)
（MIT）から取り込んだ。上流の CLI・Skill 本体は導入していない（上流の SKILL.md は
`gh issue create` を事前承認し、セッションログ由来の内容を第三者リポジトリへ起票する
指示を含むため）。

Notion への変換は実測で確認済み（Notion-Version: 2026-03-11）: `##` → `heading_2` /
`-` → `bulleted_list_item` / `- [ ]` → `to_do` / Markdown の表 → `table` /
空見出しは空のまま残る。よって md→blocks の変換器は要らない。
