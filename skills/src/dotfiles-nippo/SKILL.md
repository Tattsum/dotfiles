# 日報生成スキル

Claude Code / Cursor / Codex のセッションログと、本人の行動を確認できる外部の記録を日報にする。
**日報の主語は自分。ツールは観測できることだけを出し、内省は人間が書く**。
この分担が本スキルの設計の中心で、自動生成された振り返りを読み返しても何も残らないという
上流（nwiizo/nippo, MIT）の観察を採用している。

「学び」と「明日の小さな一歩」は例外に見えるが、書いてよいのは **digest または外部の観測に紐づけられる
ものだけ**で、そこが内省との境界になる。根拠を挙げられない一般論はモデルが書かず、
「明日の問い」の空欄として人間に残す。

## 構成（単一ロジック源）

- 事実の集約: `skill-session-digest`（`bin/skill-session-digest` が正本・PATH 上に symlink）
  - 既定は利用可能な Claude Code / Cursor / Codex をすべて収集する
  - 必要な場合だけ `--source claude|cursor|codex|all` で絞る
- 外部情報の補足: 接続済みの Calendar / Jira / Confluence / Slack / GitHub の読み取り連携・CLI。
  [取得と採用の手順](references/external-activity.md)に従い、digest とは分けて扱う
- 出力先: `~/.claude/nippo/YYYY-MM-DD.md`
- 中間ファイル: `$TMPDIR/nippo-digest-YYYY-MM-DD.json`（生成後に削除する）。
  `~/.claude/nippo/` には置かない: sandbox はここへの Bash 書き込みを許可しておらず、
  日報本体は `Write` ツール経由なので書けても、リダイレクトは `operation not permitted` で落ちる

ローカルログの集約はスクリプトに閉じ込める。
外部情報の取得には既存の読み取り連携・CLI を使い、モデルは**本人の事実の抽出・要約・言語化**を担当する。
1 日分の生ログは実測 900KB 超あり、そのまま読むとコンテキストに乗らない。

# 生成手順

## 1. 対象日を決める

引数があればそれ（`YYYY-MM-DD` / `昨日` / `8/20` 等を解釈）、無ければ今日。
ユーザーに聞き返さない。

## 2. digest を作って読む

```bash
skill-session-digest <YYYY-MM-DD> > "$TMPDIR/nippo-digest-<YYYY-MM-DD>.json" && echo "$TMPDIR"
```

`Read` は環境変数を展開しないので、echo で出た実パスを使って読む。

特定プロジェクトだけに絞る指示があれば `--project <部分一致>` を付ける。
特定エージェントだけに絞る指示があれば `--source <claude|cursor|codex>` を付ける。
生成した JSON を `Read` する。**セッションログの JSONL や Cursor の SQLite を直接読むことは絶対にしない。**

`meta.warnings` があれば、欠落したソースと継続して使えたソースを日報提示時に伝える。
1ソースの欠落だけで日報生成を止めない。`meta.source_stats[].records`（対象日に抽出できた
観測件数・セッションタイトルは含まない）が 0 でも、その日そのエージェントを使っていない
だけのことが多い。ただし「0 件しか抽出できなかった」「発話行が 1 つも無い」のいずれかの
warning が出ている場合は、**ログ形式が変わって拾えていない可能性**なので日報にそのまま添え、
統計を鵜呑みにしない。後者はそのエージェントでの作業内容が tool 集計にしか残っていない
状態なので、「やったこと」をツール実行だけから書き起こさず、記録が欠けている旨を明記する。

集約器の終了コードは意味が2つある。**混同すると異常を「記録なし」と誤報告する**ので分ける。

- `exit 1` かつ `no selected session log source is available`: 選択したソースがすべて利用不可。
  ログ未取得と記録し、外部情報の補足へ進む。digest の数値や `meta` を推測で作らない。
- それ以外の非0（`exit 2` = 引数不正 / それ以外 = 異常終了）: 「記録がありません」ではなく
  **集約器が失敗した**ことを、stderr の内容ごとユーザーに伝えて止める。

`stats.prompts_kept` と `stats.tool_calls` が両方 0 なら、その日のローカル記録は無い。
ここでは終了せず、外部情報の補足へ進む。`meta.retention_oldest` より前の日付なら、
ログが失効している旨も添える。

## 2a. 外部の記録から本人の作業を補う

[外部情報の取得と採用の手順](references/external-activity.md)を読む。
接続済みの読み取り連携・CLI があれば、対象日の本人の活動とカレンダー経由の議事録から事実を補う。
「ローカルログだけ」「オフラインで」等の指定があれば取得しない。
情報源やプロジェクトの指定は全サービスに適用する。Slack の既定は公開チャンネルのみ。
未接続・権限不足・取得失敗は欠落として伝え、利用できた情報で続ける。

ローカル記録も、外部情報から採用できる本人の事実も無い場合だけ、
「対象日の記録がありません」と伝えて終了する。資料を取得できなかった場合は、
「該当なし」と区別して不足した情報源を添える。
本人への対象日の割当だけが確認できた日も生成する。その場合の「やったこと」は
「実施記録なし」とし、割当は「明日の小さな一歩」の候補にだけ使う。

## 3. 日報を書く

`~/.claude/nippo/<YYYY-MM-DD>.md` に `Write` する。既に同名ファイルがあれば
**上書きせず**、追記か別名かをユーザーに確認する。

構成を以下に固定する。日報は読み返されて初めて価値を持つので、一目で読み切れる分量に編集する。
長さは網羅性ではなく編集の放棄を意味する。digest の情報を落とすことを恐れない。

**日付の見出しは置かない。** 日付はファイル名が担う。

```markdown
## やったこと
（プロジェクトまたは本人の作業ごとに 1 行、**最大 2 文**。「何をどこまで進めたか」だけを書く。
 ログ由来のプロジェクト名は cwd の name。外部情報だけの作業にリポジトリ名を推測で付けない。
 経緯・議論の流れ・所感は書かず、同じ作業は情報源を跨いでまとめる）

## 判断の記録
| 場面 | 選んだこと | 見送ったこと |
|---|---|---|
（**最大 5 行**。自分が選択した、または判断に関わったと確認できる決定だけ残す。
 同種の判断は 1 行にまとめる。見送った案が記録に無ければ「記録なし」。判断が無ければ表ごと省く）

## 詰まった点
（**最大 3 件・各 1 行**。エラーの再試行、方針の巻き戻し、本人の作業を阻む問題など、
 digest または外部情報から観測できるものだけ。無ければ「特になし」）

## 統計
- プロンプト {kept} 件（除去前 {total}）／ツール {tool_calls} 回（上位 3 つ）／{projects} プロジェクト・{sessions} セッション
- 稼働 HH〜HH 時（`projects[].span`）。by_hour の山と谷を 1 行で（どちらも event 時刻のみ）

## 今日の学び
（**最大 3 件・各 1 行**。digest または外部情報の本人の観測に必ず紐づける。
 「何が起きて、そこから何が言えるか」の形。紐づかない一般論は書かない）

## 明日の小さな一歩
- [ ] （**最大 2 件・各 1 行**。今日の観測から導ける具体行動。明日 15 分で着手できる粒度に限る）

## 明日の問い
- 今日いちばん時間を溶かしたのは何で、その原因はどこにあった？
  -
- 明日ひとつだけ変えるなら、何を変える？
  -
```

「明日の小さな一歩」を `- [ ]` にしているのは、チェックリストとして翌日に消化を確認できるため。

外部情報で確認できた割当は「明日の小さな一歩」の候補にし、15 分で着手できる行動に絞る。
割当だけで「やったこと」に載せず、記録された期限を明日に変更しない。
外部情報由来の行には、取得できた資料・コメント・活動の URL を出典として添える。推測した URL は載せない。

統計はセッションログのみの値であることを明記し、外部の活動件数・時間・作業を加算しない。
digest を取得できなかった場合は「セッションログ未取得」とし、数値・稼働時間を出さない。
digest の観測が 0 件の日も、外部の活動時刻だけから稼働時間を埋めない。

`projects[].sources` は、そのプロジェクトで使ったエージェントを示す。同じ git ルートは
ソースを跨いで1プロジェクトへ統合済みなので、エージェント別に重複して書かない。
Cursor は発話単位の timestamp を持たず、metadata と突合できれば `time_precision` は
`session`、できなければ transcript の更新日時を使うため `file` になる。
Cursor の時刻を時間帯の山・谷や正確な着手時刻の根拠に使わない。Cursor しか記録がない日は、
時間帯統計を推測せず、`session` なら「セッション単位の時刻のみ」、`file` なら
「ファイル更新日時ベースの低精度時刻のみ」と書く。

稼働時間は `projects[].span`（event 精度のみ）を使う。粗い時刻は `span_low_precision` に
分けてあり、**両者を足して稼働幅にしない**。`span.from` が `null` の日は event 精度の記録が
無い日なので、稼働時間を書かずに `span_low_precision` の範囲を低精度と明記して添える。

## 4. 後片付けと提示

`"$TMPDIR/nippo-digest-<日付>.json"` を `rm -f` で消し、日報のパスと本文を提示する。
外部情報の取得範囲と欠落があれば短く添える。

## 厳守事項

- **「明日の問い」に回答を書かない。** 空欄のまま残す。ここを埋めた瞬間にこのスキルの
  価値は消える。同様に「詰まった点」も、観測できない反省を足さない。
- **「今日の学び」は観測に紐づくものだけ書く。** 各行は digest 内の具体的な事実
  （時刻・回数・ファイル名・エラー内容）または外部情報で確認できる本人の行動を根拠に持つこと。根拠を挙げられない一般論
  （「早めに相談すべき」「設計を先に固めるべき」等）は、正しく見えても書かない。
- **「明日の小さな一歩」は検証できる行動だけ書く。** 「〜を意識する」「丁寧にやる」は
  翌日に達成を判定できないので禁止。何を・どこで・どれくらいやるかまで書く。
- **人格・能力の評価を書かない。** 「集中力が続かなかった」等の性質への言及はしない。
  観測できるのは行動と結果だけで、そこから人格を推し量るのはこのツールの役割ではない。
- **統計の数値は digest から直接引用し、再計算しない。** 件数を数え直したり推定したりしない。
- **日付は `meta.date` を使う。** digest 未取得時のみ手順 1 の対象日を使う。実行日から計算し直さない。
- **digest または外部情報で確認できない本人の作業を書かない。** プロジェクト名・ファイル名・コミット内容を推測で
  補完しない。情報が薄い日は薄いまま出す。
- **参考書籍・記事・推測した URL を紹介しない。** 取得済みの外部情報の URL は出典としてのみ使う。
- **Python を使わない。** 追加の集計が要るなら `jq` で digest に対して行う。
- **リポジトリ内に日報を書かない。** 出力は `~/.claude/nippo/` 固定。digest には
  private リポジトリ名・ブランチ名・プロンプト本文（顧客名・案件名を含みうる）が
  そのまま入る。実測で 1 日分の 3 割強が社内固有名を含む。dotfiles は public。
- **Bash 出力が途中で切れていたら、その先を推測しない。** 再実行する。

## 対象範囲（意図的にやらないこと）

- **生成入力はローカルログと、本人の対象日の活動を裏付ける外部情報に限る**。
  クラウド上のエージェント履歴や、本人・対象日と無関係な文書の横断検索は行わない。
- **サブエージェントログは集計外**。Claude の `agent-*.jsonl`、Cursor の `subagents/`、
  Codex の subagent source を除外する。日報の主語は人間の作業で、内部のツール実行まで
  数えると実態から乖離する。
- **週次・月次・長期トレンドは扱わない**。ログ保持は実測で約 1 ヶ月しかなく、
  90 日レンジの集計は「入力が沈黙したまま、それらしい出力が出る」形で劣化する。
  必要になったら、生ログではなく蓄積済みの `~/.claude/nippo/*.md` を入力にすること。
- **`~/.claude/history.jsonl` は見ない**。あれはプロンプトのみで行動が無く、
  `prompt-pattern-scan` が別目的で使う入力。

プロジェクトは cwd を git のトップレベルに畳んで数えている。**git worktree は別プロジェクト
として並ぶ**（`<repo>` と `<repo>-wt-pr1234` のように別々の行になる）。同じリポジトリの
作業だと分かる場合は、日報側で 1 つの見出しにまとめてよい。
Cursor の transcript と metadata を突合できない場合は `cursor://<project>` という限定的な
識別子になる。その場合、同じリポジトリだと digest だけから断定できないため推測で統合しない。
