# Must 候補の反証

統合で重複を除いたあとの security の Must 候補だけを、反証エージェント 1 体にまとめて渡し、Must のまま出してよいかを検証する。単体実行でも、`dotfiles-code-review` 経由でも同じ契約を使う。検出と検証を別の担当に分けるのは、検出側が自分の指摘を過大に見積もる偏りを避けるため（NIST SP 800-115 の考え方: <https://csrc.nist.gov/pubs/sp/800/115/final>）。

## 実行条件

- 反証の対象は「security の Must 候補（観点 `到達性・公開範囲の変更` を除く）」。到達性担当の指摘は Sink を持たず、到達性の観点で到達性担当を反証すると循環するため。
- 対象が 1 件以上あるときだけ起動する。Should / Nice は反証しない: 件数に比例してエージェントが増え、過剰な棄却で見落としが増えるため。
- 補助扱い。このファイルが読めない・反証エージェントが失敗・出力が契約に沿わない場合は止めず、`## 🧪 反証で格下げ・取り下げた指摘` 節に `未実施（<理由>）` と書いて Must を維持する。網羅性は変わらない。黙って省略しない（「反証して全件維持」と「反証していない」を区別するため）。

## 起動

`general-purpose` サブエージェントを 1 体、次のプロンプトで起動する。`<MUST_CANDIDATES>` は各候補の `[path:line]`・観点・問題点・Source→Sink・到達性・重要度案、`<REACHABILITY_CONTEXT>` は到達性コンテキストの JSON（未解決なら「未解決（理由）」）、`<TARGET_FILES>` と `<base>` は統合側が持つ値をそのまま入れる。

```text
あなたは /review-web-security の反証担当です。レビューのみ行い、ファイルは編集しないでください。
これは差分の所有者側による防御目的のレビューです。攻撃手順・PoC は書かず、証拠は path:line で示してください。

最初に次を Read すること:
- ~/.claude/skills/review-web-security/references/must-verification.md（判定の形式と規則）
- ~/.claude/skills/review-web-security/references/output-discipline.md（重要度案の付け方）

Must 候補:
<MUST_CANDIDATES>

到達性コンテキスト:
<REACHABILITY_CONTEXT>

対象ファイル:
<TARGET_FILES>

ベースブランチ: <base>

手順:
1. 候補ごとに、指摘のファイルと Source→Sink の経路を Read で読む。差分に無い呼び出し元・上流の検証も Read でたどる。
2. 「反証の観点」の 2 つで、Must を崩せる証拠があるかを探す。
3. 判定は must-verification.md の「判定の出力」に従う。証拠が無ければ維持する。
```

## 反証の観点

- 到達性: 記載の攻撃者の立ち位置から入口に届かない、または統制（WAF の Block ルール・エッジ認証・IP 制限・セキュリティグループ・private network）で塞がれていることを、到達性コンテキストの evidence・IaC の path:line・コードの path:line で示せるか。count-only の WAF・自己申告値・確認されていない統制は証拠にならない。
- コードの正確性: 指摘の Sink が path:line に実在するか、信頼できない値が本当に届くか（上流でパラメータ化・検証・認可されていないか）を path:line で示す。

## 判定の出力

候補ごとに次を出す。見出しと項目名は統合処理が逐語で照合するので変えない。

```text
### [path:line]
- **判定**: 維持 / 格下げ（Must→Should）/ 格下げ（Must→Nice）/ 取り下げ
- **反証の観点**: 到達性 / コードの正確性
- **証拠**: path:line / IaC path:line / ライブ <query>: <項目>=<値>（維持なら「なし」）
- **再評価**: Impact=… × Likelihood=… → …（格下げ時のみ）
- **理由**: 1〜2 文
```

最後に次の1節を付ける。

```text
#### 確認できなかった範囲
- （読めなかった IaC・呼び出し元、ライブ未確認の統制等。無ければ「なし」）
```

## 規則

- 格下げ・取り下げには証拠が必須。証拠が無ければ維持する。賛成する必要はないが、推測で崩さない。
- 再評価は `output-discipline.md` の Impact × Likelihood の表で行い、Likelihood は証拠で示せた障壁だけ数える。
- 到達性だけを理由に、下限（根本原因）が適用された Must を Must 未満へ下げない。下げられるのは、コードの正確性で根本原因自体（Sink の不在・上流での無害化）が否定されたときだけ。到達性が低くても根本原因は残り、統制の変更で再び露出するため。
- 到達性コンテキストが未解決のときは、到達性の観点で格下げしない。コードの正確性だけで判定する。
- ライブの証拠は到達性コンテキストに記録されたものだけを使う。反証エージェントが自分で AWS 等へ問い合わせない: ライブ参照の入口は `review-reachability` に一本化しているため。

## 統合側の扱い

- 維持: そのまま Must に残す。
- 格下げ: 新しい重要度へ移し、指摘に「反証により格下げ（証拠: …）」を注記する。
- 取り下げ: 指摘リストから外し、`## 🧪 反証で格下げ・取り下げた指摘` 節に証拠つきで列挙する。黙って消さない。
- `## 🧪 反証で格下げ・取り下げた指摘` 節の先頭行は次の 3 状態のどれかを固定文言で書く。
  - `対象なし（security の Must 候補 0 件）`
  - `実施: N 件を検証、格下げ X 件・取り下げ Y 件`（その下に格下げ・取り下げを証拠つきで列挙する。全件維持なら X=0, Y=0）
  - `未実施（理由）`
- 候補単位で判定が契約の形式に沿わなかったものは維持とし、その Must の詳細行の末尾に「（反証: 未実施・出力不完全）」と注記する（🧪 節には書かない）。
- 反証エージェントの `確認できなかった範囲` は、新しい見出しを作らず、統合側の既存の `## 🔍 確認できなかった範囲` 節へ各担当のものと重複を除いてまとめる。
