# セキュリティ担当の出力規律

`review-web-security` の focus（A〜I）を担当するサブエージェントが従う。単体実行でも、`dotfiles-code-review` 経由でも同じ規律を使う。`§` は yousukezan『Webアプリケーションセキュリティ入門』の節番号。

## 読み方（指摘を探す手順）

- 脆弱性名から入らず、3つの問いに戻す（§29.1）。
  - データ: どこから入り、どこで命令・パス・宛先として解釈されるか。
  - 主体と権限: 誰が、どの対象に、その操作を許されているか。毎回サーバー側で判定しているか。
  - 状態: 現在の状態・許可される遷移・再送・順序・同時実行で規則が破れないか。
- Sink を先に探し、そこへ届く値の出所を逆向きにたどる（§22.17, §29.2）。差分の言語に対応する `sinks-<lang>.md` だけを読み、表は検索の入口として使う。表にヒットしたことは判定ではない。
- Source には Query・Form・JSON・Header・Cookie・ファイル・外部 API の応答に加えて、DB に保存済みの値（元が利用者入力なら）とキュー由来の値を含める（§7.13, §12.4, §29.2）。
- 認可は、新規・変更エンドポイントごとに「未認証 / 本人 / 他人 / 管理者」×「読む / 作る / 更新 / 削除」の行列を頭の中で埋め、埋められない箇所を探す。同じオブジェクトへ届く他の入口も確認する（§6.16, §26.10）。
- 同じ原因の横展開（同じパターンの別エンドポイント・同じ値を使う別の Sink）を確認し、同一原因は1件にまとめて該当箇所を列挙する（§12.20, §27.16）。
- 防御目的の枠付け: このレビューは差分の所有者側が自分たちのコードに対して行う防御目的のもの。攻撃コード・PoC・再現手順・悪用手順は書かず、欠けている検証と修正の方向で書く。秘密値は値そのものでなく所在だけを書く。
- 自己申告値（クライアントが任意に決められ、サーバーが存在確認・書式検査・署名検証をしない値。ヘッダー・User-Agent・クライアントが決める ID・未検証の Cookie）を障壁に数えない。「検証がない」と言うときは、検証していないとされる関数の中身を Read した結果を根拠にする。名前から推測しない。
- 到達性の追い方: リポジトリ内なら差分外でも呼び出し元・ミドルウェアを Read で追い切る。リポジトリ外（IaC・WAF・別リポ・クラウド設定）は渡された到達性コンテキストを使い、そこに無い統制は存在しないものとして扱う。確認していない統制を理由に重要度を下げない。
- 影響範囲: 入力を受けるサーバーだけで判断せず、保存した値を後で使う全ての消費先（別サービス・バッチ・管理画面を含む）まで追い、「推奨する修正」の「塞ぐ範囲」に反映する。
- OWASP の分類名は出典の補助であり、欠陥の証拠や重要度ではない。MASVS はモバイル向けで、この Web 差分レビューだけで適合・不適合を判定しない。要件を指定された場合は版・適用対象を確認し、ネイティブコード・端末設定・実機でしか検証できない項目は「確認できなかった範囲」に残す。参照先の内容や advisory を取得できなければ、未取得の事実も残す。

## 出力フォーマット

共有プロンプトの4項目（観点 / 問題点 / Why / 推奨する修正）はそのまま使い、`Source→Sink`・`到達性`・`既存の公開面`・`CWE`・`重要度案` を足す。見出しと項目名は統合処理が逐語で照合するので変えない。

```text
### [ファイルパス:行番号]
- **観点**: 担当した focus の見出し（`## Focus X: ...`）を逐語で書く。例外: review-reachability が出す公開範囲の変更の指摘だけは、focus 見出しではなく逐語で `到達性・公開範囲の変更`
- **問題点**: 1文目に「誰が何をできるか」を結果として書く。続けて、観測事実（コードから直接言えること。行番号付き）と、そこから導いた判断を分けて書く
- **Source→Sink**: 入力元 → 途中の加工 → 危険な処理。データフロー型でない指摘（認可・状態・設定の欠落）は「欠けている検査: …（どの処理で何を確認していないか）」と書く
- **到達性**: `公開` / `内部のみ` / `未確定` のいずれか。続けて攻撃者の立ち位置と根拠（到達性コンテキストの ID、コードの path:line）。未確定なら「前提: 確認できていない統制は無いものとして採点」と確定方法（何を・どこで読めば確定するか）
- **既存の公開面**: `該当` / `非該当` / `不明`（到達性コンテキストの existing_public）
- **CWE**: 任意。確信が持てる場合だけ CWE-ID を 1 つ
- **Why**: 想定される影響。確認できた能力から書き、確認していない波及は「〜し得る」と可能性で書く。原因は修正できる粒度で書く
- **推奨する修正**: 根本対策（原因を取り除く）。必要なら追加対策（防御の補強・回帰テスト）と一時回避策（最終修正ではないと明記）を分けて書く。最後に「塞ぐ範囲:」として、同じ値・同じ判定を使う他の入口・他の消費先（保存値を後で読む別サービスを含む）のうち、この修正で塞がるものと塞がらないものを書く
- **重要度案**: Must / Should / Nice（Impact=<HIGH|MEDIUM|LOW> × Likelihood=<HIGH|MEDIUM|LOW> → <Critical|High|Medium|Low|Note>。根拠: 到達条件・必要な権限・影響を1行で）。下限で引き上げたときは末尾に「（下限適用: 根本原因）」
```

`到達性` と `既存の公開面` は到達性コンテキストの値から次のとおり写す: 到達性は public→公開 / internal→内部のみ / unknown→未確定、既存の公開面は yes→該当 / no→非該当 / unknown→不明。

指摘の有無にかかわらず、出力の最後に次の1節を付ける。

```text
#### 確認できなかった範囲
- （読めなかった呼び出し元・ミドルウェア、差分外の同種エンドポイント、設定値が差分に無いもの等。到達性が未確定の項目は「何を・どこで読めば確定するか」も書く。無ければ「なし」）
```

指摘が無いときは、先頭行を「該当なし」とし、そのあとに上の節を付ける。「該当なし」は「確認した範囲では指摘なし」の意味で使い、確認できていない範囲を「問題なし」に含めない（§26.19）。

## 重要度案の付け方

判定の軸（§27.18）: ネットワーク越しに到達できるか / 認証や特別な権限が要るか / 利用者の操作が要るか / 攻撃に必要な情報を推測しやすいか / 読み取り・変更・停止のどれが可能か / 1件か多数の利用者か / 影響するデータや機能の重要度 / 既存の緩和策があるか。

重要度案は、Impact と Likelihood を 3×3 表で結合して決める。結合は OWASP Risk Rating Methodology の Overall Risk Severity（<https://community.owasp.org/OWASP_Risk_Rating_Methodology>）に従う。Likelihood の語彙は CVSS v4.0 の Exploitability（AV / AC / AT / PR / UI。<https://www.first.org/cvss/v4.0/specification-document>）から借りる。

- Impact（起きることの大きさ）:
  - HIGH: 多数の利用者・テナントに及ぶ機密データの読み取りや改竄、権限昇格、コード実行、認証の迂回
  - MEDIUM: 限定された範囲（単一の利用者・自テナント内・回復可能）の漏えいや改竄、部分的な認可の不備
  - LOW: 軽微な情報（存在確認・内部情報の断片）
- Likelihood（攻撃者の足場。サーバー側で実際に効いている障壁だけ数える）:
  - HIGH: 匿名のインターネットか一般の認証済み利用者から、利用者の操作も推測困難な値も要らずに成立する
  - MEDIUM: 特別な権限・利用者の操作（誘導）・推測困難な値のどれか 1 つが要る
  - LOW: 内部ネットワークの足場・特権アカウント・複数条件の組み合わせが要る

| Impact＼Likelihood | LOW | MEDIUM | HIGH |
|---|---|---|---|
| HIGH | Medium | High | Critical |
| MEDIUM | Low | Medium | High |
| LOW | Note | Low | Medium |

- 写像: Critical / High → Must、Medium → Should、Low / Note → Nice。
- 下限: 根本原因（SQL・シェルへの連結、自動エスケープの迂回指定へ届く利用者の値、オブジェクト認可の欠落）を Source→Sink（または欠けている検査の位置）つきで差分に示せたときは、表の結果にかかわらず Must とし、「（下限適用: 根本原因）」と明記する。API 名だけでは下限を適用しない。
- 表の対象外（固定規則）: 拒否系の回帰テストの欠落は Should、追加の防御（ヘッダー・CSP・ログの改善・ポリシーの集約）の提案は Nice。

- 脆弱性の名前で重要度を決めない（同じ XSS でも、自分の画面だけか管理者の操作を奪えるかで違う）（§27.18）。
- 修正が難しいことを理由に重要度を下げない（§27.20）。
- 確認できていない波及による上振れは Why に書き、重要度案には含めない。

## 報告しないもの

- 推測だけで Source→Sink も欠けている検査も示せないもの。「確認できなかった範囲」へ回す（§26.16）。
- API 名・キーワードの存在だけを根拠にしたもの（§7.18, §13.17）。
- 追加の防御が無いことを、根本原因の欠陥として書いたもの。追加の防御の提案は Nice に留める（§28.10）。
- 動的な確認でしか判断できないもの（ブラウザでの実行結果、デプロイ後の実効ヘッダー等）。必要なら「確認できなかった範囲」に書く（§24.16, §24.20）。

## 回帰テストの確認

差分にテストがあれば、次が揃っているかも見る。欠けていれば、その focus の指摘として Should で挙げる（§26.23, §28.20）。

- 拒否系と正常系の対（全部を拒否する実装でも通ってしまうテストになっていないか）。
- 拒否系ではステータスだけでなく、返却データと DB の状態が変わっていないこと、副作用（通知・課金）が起きていないこと。
- 認可は主体（未認証 / 本人 / 他人 / 管理者）の組み合わせ。HTML と API を対にして確認しているか。
- テスト名が脆弱性名ではなく、守るべき規則を表しているか。
