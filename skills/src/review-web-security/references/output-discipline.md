# セキュリティ担当の出力規律

`review-web-security` の focus（A〜I）を担当するサブエージェントが従う。単体実行でも、言語別オーケストレーター（`dotfiles-go-review` / `dotfiles-php-laravel-review` / `dotfiles-ts-review`）経由でも同じ規律を使う。`§` は yousukezan『Webアプリケーションセキュリティ入門』の節番号。

## 読み方（指摘を探す手順）

- 脆弱性名から入らず、3つの問いに戻す（§29.1）。
  - データ: どこから入り、どこで命令・パス・宛先として解釈されるか。
  - 主体と権限: 誰が、どの対象に、その操作を許されているか。毎回サーバー側で判定しているか。
  - 状態: 現在の状態・許可される遷移・再送・順序・同時実行で規則が破れないか。
- Sink を先に探し、そこへ届く値の出所を逆向きにたどる（§22.17, §29.2）。差分の言語に対応する `sinks-<lang>.md` だけを読み、表は検索の入口として使う。表にヒットしたことは判定ではない。
- Source には Query・Form・JSON・Header・Cookie・ファイル・外部 API の応答に加えて、DB に保存済みの値（元が利用者入力なら）とキュー由来の値を含める（§7.13, §12.4, §29.2）。
- 認可は、新規・変更エンドポイントごとに「未認証 / 本人 / 他人 / 管理者」×「読む / 作る / 更新 / 削除」の行列を頭の中で埋め、埋められない箇所を探す。同じオブジェクトへ届く他の入口も確認する（§6.16, §26.10）。
- 同じ原因の横展開（同じパターンの別エンドポイント・同じ値を使う別の Sink）を確認し、同一原因は1件にまとめて該当箇所を列挙する（§12.20, §27.16）。

## 出力フォーマット

共有プロンプトの4項目（観点 / 問題点 / Why / 推奨する修正）はそのまま使い、`Source→Sink` と `重要度案` を足す。見出しと項目名は統合処理が逐語で照合するので変えない。

```text
### [ファイルパス:行番号]
- **観点**: 担当した focus の見出し（`## Focus X: ...`）を逐語で書く
- **問題点**: 1文目に「誰が何をできるか」を結果として書く。続けて、観測事実（コードから直接言えること。行番号付き）と、そこから導いた判断を分けて書く
- **Source→Sink**: 入力元 → 途中の加工 → 危険な処理。データフロー型でない指摘（認可・状態・設定の欠落）は「欠けている検査: …（どの処理で何を確認していないか）」と書く
- **Why**: 想定される影響。確認できた能力から書き、確認していない波及は「〜し得る」と可能性で書く。原因は修正できる粒度で書く
- **推奨する修正**: 根本対策（原因を取り除く）。必要なら追加対策（防御の補強・回帰テスト）と一時回避策（最終修正ではないと明記）を分けて書く
- **重要度案**: Must / Should / Nice（根拠: 到達条件・必要な権限・影響を1行で）
```

指摘の有無にかかわらず、出力の最後に次の1節を付ける。

```text
#### 確認できなかった範囲
- （読めなかった呼び出し元・ミドルウェア、差分外の同種エンドポイント、設定値が差分に無いもの等。無ければ「なし」）
```

指摘が無いときは、先頭行を「該当なし」とし、そのあとに上の節を付ける。「該当なし」は「確認した範囲では指摘なし」の意味で使い、確認できていない範囲を「問題なし」に含めない（§26.19）。

## 重要度案の付け方

判定の軸（§27.18）: ネットワーク越しに到達できるか / 認証や特別な権限が要るか / 利用者の操作が要るか / 攻撃に必要な情報を推測しやすいか / 読み取り・変更・停止のどれが可能か / 1件か多数の利用者か / 影響するデータや機能の重要度 / 既存の緩和策があるか。

| 重要度案 | 目安 |
|---|---|
| Must | 認証不要または低い権限で到達でき、機密データの読み取り・他者データの変更・権限昇格・コード実行のいずれかが成立する。または根本原因（SQL への連結、シェル経由の連結、自動エスケープの迂回指定へ届く利用者の値、オブジェクト認可の欠落）が差分で確認できる |
| Should | 成立に追加条件（特別な権限・利用者の操作・推測が難しい値）が要る、影響が限定的、緩和策はあるが根本原因が残る、または拒否系の回帰テストが欠けている |
| Nice | 追加の防御（ヘッダー・CSP・ログの改善・ポリシーの集約）の提案。根本原因がすでに取り除かれている場合の補強 |

- 脆弱性の名前で重要度を決めない（同じ XSS でも、自分の画面だけか管理者の操作を奪えるかで違う）（§27.18）。
- 修正が難しいことを理由に重要度を下げない（§27.20）。
- 確認できていない波及による上振れは Why に書き、重要度案には含めない。

## 報告しないもの

- 推測だけで Source→Sink も欠けている検査も示せないもの。「確認できなかった範囲」へ回す（§26.16）。
- API 名・キーワードの存在だけを根拠にしたもの（§7.18, §13.17）。
- 追加の防御が無いことを、根本原因の欠陥として書いたもの。追加の防御の提案は Nice に留める（§28.10）。
- 動的な確認でしか判断できないもの（ブラウザでの実行結果、デプロイ後の実効ヘッダー等）。必要なら「確認できなかった範囲」に書く（§24.16, §24.20）。

## 回帰テストの確認

差分にテストがあれば、次が揃っているかも見る。欠けていれば、その focus の指摘として Should で挙げる（§26.23, §28.20）。

- 拒否系と正常系の対（全部を拒否する実装でも通ってしまうテストになっていないか）。
- 拒否系ではステータスだけでなく、返却データと DB の状態が変わっていないこと、副作用（通知・課金）が起きていないこと。
- 認可は主体（未認証 / 本人 / 他人 / 管理者）の組み合わせ。HTML と API を対にして確認しているか。
- テスト名が脆弱性名ではなく、守るべき規則を表しているか。
