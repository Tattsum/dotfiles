# Web Security Focus Blocks

Use one block per subagent. Keep each subagent constrained to its assigned block.

各項目末尾の `§` は、yousukezan『Webアプリケーションセキュリティ入門』（<https://bogus.jp/webapp_security_review.pdf>）の節番号。`既存 TS-A` / `既存 PHP-B` 等は、このスキルへ統合して廃止した旧 review-ts-security / review-php-security の Focus A / B 由来。言語別の API 名は focus に書かず `sinks-<lang>.md` に置く。

## Focus A: インジェクション（データが別のインタプリタで命令として解釈される境界）

SQL・OS コマンド・テンプレートエンジン・XML パーサー・デシリアライザー・ログ行へ、信頼できない値が命令として渡る経路をレビューする。

- SQL の値はバインドパラメータで渡し、外部入力を SQL 文字列へ連結・埋め込みしない。SELECT 以外の INSERT / UPDATE / DELETE、保存済みの値を後で連結するバッチ（second-order）、保守スクリプトも同じ。ORM から raw API へ降りる箇所は、最終的に構文として渡るか値として渡るかで判断する（§7.3, §7.7, §7.8, §7.13）。
- テーブル名・列名・ORDER BY・ASC / DESC はバインドできないため、許可リストのマップで既知の値へ変換し、不明値は拒否する。LIKE の `%` `_` は仕様に応じてエスケープする（SQLi 対策とは別の目的）（§7.10, §7.12）。
- OS コマンドは、まず言語の標準 API で置き換えられないかを疑う。外部プロセスが必要なら実行ファイルを固定し、シェルを経由せず引数を配列で渡す。外部入力を連結した文字列をシェルへ渡す経路は最重要の警告（§13.2, §13.7-13.9）。
- シェルを使わなくても引数注入は残る。利用者の値が `-` で始まるとオプションとして解釈され得るので、固定オプションとオペランドを分け、対応 CLI なら `--` で終端し、有限値は許可リストで固定オプションへ変換する。エスケープ関数を第一選択にしない。子プロセスの環境変数・作業ディレクトリ・timeout・出力サイズも固定または制限する（§13.10-13.14）。
- テンプレートの Source は開発者管理の固定値にし、利用者入力はデータ（コンテキスト）として渡す。文字列からテンプレートをコンパイルする API に、外部入力（保存済みの通知文、メール・PDF・帳票の文面、プレビュー機能を含む）が届かないか。テンプレート名も許可リストで選ぶ（§14.3, §14.6, §14.9, §14.11）。
- XML を受け付けるなら DTD・外部エンティティ・XInclude を明示的に無効化し、使っているパーサーの実体とオプションで判断する（Schema 検証は XXE 対策にならない）。SVG・Office 文書・フィードなど XML を内包する形式も対象。XPath は変数バインドを使い、XML は文字列連結でなく API で組み立てる（§16.8-16.10, §16.13）。
- 信頼できないバイト列を、オブジェクトを復元する形式のデシリアライザーへ渡さない。署名・暗号化・Base64 は代替にならない。YAML は安全なローダーを使い、JSON でもサイズ・入れ子・未知フィールドを検証する。キュー・キャッシュ・DB 由来の値は、保存場所ではなく生成経路と書き込み権限で信頼を判断する（§16.14-16.19）。
- ユーザー名・User-Agent・URL・ファイル名などの信頼できない値を、改行や区切り文字を含んだままテキストログへ連結しない。構造化ロガーの属性として渡し、長さを制限する。JSON ログも文字列連結で組み立てない（§25.11, §25.14）。

誤検知の注意:
- raw SQL API・exec 系・文字列からテンプレートをコンパイルする API の名前があるだけで脆弱と判断しない。固定 SQL と値のバインド、固定文字列だけのシェル実行、固定 Source へデータを渡すテンプレートは問題ない。Source から Sink まで信頼できない値が届く経路を示せるときだけ指摘する（§7.9, §13.4, §14.5）。
- 入力検証・禁止文字・長さ制限・詳細エラーの非表示・DB の最小権限・WAF は、パラメータ化や argv 化の代わりにならない。これらがあることを連結を許容する理由にしない（§7.11, §7.15, §13.16）。
- 「管理者専用」「DB から読んだ値」でも修正対象。ただし影響は確認できた範囲で書き、「RCE 確定」のような断定をしない（§13.16, §13.19, §14.8）。

Report only injection paths where an untrusted Source reaches the interpreter Sink; state the Source→Sink path.

## Focus B: XSS とクライアントサイド（出力文脈とブラウザの能力）

HTML / DOM / URL への出力、ブラウザ上の信頼境界（postMessage・Storage・埋め込み）、CORS とセキュリティヘッダーをレビューする。

- 出力は文脈ごとに処理が違う（HTML 本文・属性・JavaScript・URL・CSS）。フレームワークの自動エスケープを迂回する指定に信頼できない値が届かないか。on* 属性・インライン script・style に動的値を入れない。HTML が要件なら保守されたサニタイザと明示の許可リストを使い、正規表現での自作除去はしない（§8.5, §8.9, §8.10, 既存 TS-A / PHP-A）。
- innerHTML / outerHTML / insertAdjacentHTML / document.write と、eval / new Function / 文字列を渡す setTimeout・setInterval に、URL（search / hash）・API 応答・Web Storage・postMessage 由来の値を渡さない。表示は textContent かフレームワークのバインディングにする（§8.8, §22.4-22.6）。
- 外部入力を href / src / window.open / location / リダイレクト先に使うなら scheme を許可リスト（http / https / 相対）で検証する（HTML エスケープでは `javascript:` を無害化できない）。リダイレクト先は相対パスに限定して `//` や `\` で始まる値を拒否し、外部 URL は host を正規化して完全一致で照合する。外部入力からリクエスト先の path / method を組み立てて送信しない（client-side CSRF）（§8.9, §22.7, §22.8, 既存 TS-A / TS-B）。
- 保存時に HTML へ変換せず、出力時に文脈に応じて処理する。JSON API 自体が安全でも、消費側（Web 画面・管理画面・HTML メール・ログビューア）で HTML として出していないか。管理画面も信頼しない（§8.10, §8.11, §8.14）。
- postMessage は送信側で targetOrigin を具体的な Origin にし、受信側で event.origin を完全一致で確認したうえで event.data の型と項目を検証する。信頼できないキーで再帰 merge・深いコピー・動的プロパティ代入をしない（プロトタイプ汚染）。Web Storage にトークンや機微データを置かず、保存値を認可の根拠にしない（§22.9, §22.10, §22.13, 既存 TS-B）。
- `<iframe>` の sandbox は最も厳しい値から始めて必要なトークンだけを足す。`allow-scripts` と `allow-same-origin` の併用は sandbox を実質無効にするため既定にしない。埋め込み先 host は許可リストにし、利用者入力由来の script / style の動的注入やサードパーティ埋め込みに注意する（既存 TS-A）。
- リクエストの Origin を Access-Control-Allow-Origin へ反射しない（Credentials 付きは特に）。許可は scheme・host・port の完全一致で照合し、前方・後方一致や緩い正規表現、`null` の許可を避ける。Origin を動的に返すなら `Vary: Origin` を付ける。CORS は認証・認可・CSRF 対策の代わりにならない（§18.4, §18.11-18.13）。
- CSP の script-src に、違反を消す目的で `'unsafe-inline'` / `'unsafe-eval'` / `*` を足さない（インライン script は外部化し、必要なら nonce をレスポンスごとに生成する）。frame-ancestors と frame-src の向きを取り違えない。nosniff と正しい Content-Type、Referrer-Policy、認証後・個人向けレスポンスの Cache-Control（no-store / private）を確認する。共通ヘッダーはエラー・リダイレクト・ダウンロードにも付く層で設定する（§17.3-17.12, §17.14）。

誤検知の注意:
- 自動エスケープの迂回指定があるだけで断定しない。値の出所（開発者管理の固定 HTML か、利用者由来か）を追う。レスポンスに値が含まれていても、文脈に合うエスケープ済みなら問題ない（§8.5, §8.6）。
- 正しい Content-Type で返す JSON 自体は XSS ではなく、問題は消費側。location.hash 等の Source があるだけでも脆弱ではなく、Sink まで届いて初めて指摘する。decodeURIComponent・Base64 decode・JSON.parse は形式を戻すだけで安全化ではない（§8.11, §22.2, §22.17）。
- CSP・HttpOnly・nosniff があることを Sink を許容する理由にしない。逆に CSP が無いことは XSS があることを意味しない。ヘッダーの欠落は攻撃経路と分けて書き、古いヘッダー（X-XSS-Protection 等）の欠落は単独で指摘しない（§8.12, §17.13, §17.17）。
- `Access-Control-Allow-Origin: *` は認証不要の公開データなら仕様どおり。指摘するのは機密レスポンスを信頼できない Origin と共有できる場合（反射・Credentials 付き・`null` 許可）（§18.9, §18.18）。

Report only sinks reachable from untrusted input and browser-boundary settings that expose sensitive responses; state the Source→Sink path or the exact setting.

## Focus C: 認証とセッション（CSRF を含む）

パスワード保存・アカウント列挙・試行制限・リセットと復旧・セッションのライフサイクル・Cookie・CSRF・トークン検証をレビューする。

- パスワードは専用の方式（Argon2id / bcrypt / scrypt / PBKDF2）をライブラリ経由で保存する。平文・可逆暗号・汎用ハッシュ単独（SHA-256 / MD5）、自作の salt や独自の連結は不可。コストはログイン成功時の再ハッシュ（needs-rehash）で更新できるようにする（§4.5-4.7）。
- ログイン・登録・パスワードリセットで、未登録・パスワード違い・無効化の違いをメッセージ・ステータス・レスポンス構造で出し分けない（アカウント列挙）。ユーザーが存在しないときに検証処理を丸ごと飛ばす早期 return にも注意する（§4.9, §4.11, §21.8）。
- ログイン・リセット・MFA 検証に、アカウント単位と送信元単位の試行制限を掛ける。永久ロックはロックアウト DoS になるため段階的な待機や一時制限にする。ハッシュの強度は試行制限の代わりにならない（§4.12）。
- リセットトークンは CSPRNG で十分な長さにし、利用者と目的に紐付け、短い期限・一回限り・保存時はハッシュ化する。リセット URL は受信した Host ヘッダーではなく設定済みの Origin から組み立てる。MFA の登録・解除・リカバリーコード再発行、メール・パスワード変更、API キー発行などの重要操作は、直近の認証時刻を見て再認証を求める（§4.13, §4.14, §5.14）。
- 認証成功・権限昇格・MFA 完了の各境界でセッション ID を再生成し、認証前の状態を破棄する（固定化対策）。署名だけのクライアント側セッション（署名付き Cookie・JWT の payload）に秘密を入れない。セッション ID やトークンを URL に入れない（§5.2, §5.10, §5.15）。
- セッション Cookie は Secure・HttpOnly・SameSite（Lax 以上）・Domain なしにする。ローカル用に緩めた設定（Secure 無効）が本番に流れ込まない既定値にする。アイドル期限・絶対期限・再認証期限を区別し、ログアウトや強制失効の要件があるならサーバー側で無効化する（§5.8, §5.11-5.13）。
- Cookie 認証の状態変更（POST / PUT / PATCH / DELETE。ログイン・ログアウト・アップロード・JSON API を含む）は、共通層で推測困難なトークンを定数時間比較で検証する。GET で状態を変えない。トークンを URL やログに出さない。除外（Webhook 等）は署名・タイムスタンプ・リプレイ防止の代替認証と同時に入れ、「除外を足すだけ」の差分は止める（§9.4-9.11, §9.17, 既存 TS-B）。
- JWT は署名検証を必須にし、許可アルゴリズムを固定し、exp / iss / aud を検証する。OAuth / OIDC は保守されたライブラリで Authorization Code + PKCE を使い、state / nonce を取引ごとに検証し、redirect URI を固定する。メールアドレスの一致だけで外部アカウントを既存アカウントへ結合しない（§5.16, §19.9, §29.17）。

誤検知の注意:
- SameSite は CSRF トークンの代わりではなく、HttpOnly は XSS を無害にしない。「JSON API だから CSRF は不要」とは限らないが、Authorization ヘッダーで Bearer を明示送信する設計は条件が異なる（§5.8, §9.11）。
- ローカル HTTP 用の Secure 無効自体は開発用の例外。問題は本番に流れ込むことと既定値が緩いこと（§5.3, §24.15）。
- 文字種の強制が無いこと、Pepper が無いことは単独では指摘しない。応答時間の差による列挙は改善余地であり、それだけで Must にしない。CSRF 用に認証前からセッション Cookie が発行されること自体は問題ではない（§4.6, §4.8, §4.9, §5.4）。
- 「JWT に変えれば安全」「Cookie だから危険」と単純化しない。保存先・読む主体・送信先で判断する（§5.16）。

Report only concrete authentication, session, or CSRF gaps visible in the diff; state which check is missing and where.

## Focus D: 認可と API 契約

オブジェクト単位・機能単位・プロパティ単位の認可、テナント分離、入口間の一貫性、API の入出力契約をレビューする。

- リクエストごとにサーバー側で、誰が（Subject）・どの対象に（Object）・何を（Action）・どの関係と状態で（Context）を判定する。ログイン済みの確認だけで、ID から取得したオブジェクトを返したり更新したりしない（BOLA / IDOR）。UUID 化は推測を難しくするだけで認可ではない（§6.1, §6.7, §19.4, §19.5, 既存 TS-B / PHP-B）。
- 所有者・関係・状態・テナント ID を取得条件（WHERE やスコープ）に含め、対象外の行を最初から取得しない。マルチテナントでは、すべてのクエリにテナント条件が付いているか（§6.12, 既存 PHP-B）。
- 同じオブジェクトに届くすべての入口（HTML と JSON API、一覧・検索・オートコンプリート、エクスポート、添付ファイル、GraphQL の Resolver、WebSocket のメッセージ、バックグラウンドジョブ）に同じポリシーを適用する。ポリシーは共通の関数やスコープに集約する（§6.14, §29.3, §29.19）。
- 管理・特権機能は UI の非表示ではなく、サーバー側のミドルウェアやポリシーで守る。新しいルートにガードが付いているか。明示的に許可できたときだけ許可する（Deny by default）。最後の管理者の削除や自分自身の降格による権限ロックアウトを防ぐ（§6.11, §6.15, 既存 TS-B）。
- リクエスト本文をモデルへ一括代入しない（マスアサインメント）。所有者 ID・ロール・状態・価格・承認者など、サーバーが決められる値は受け取らず、認証済みの主体と DB から決める。更新できる項目は許可リストで取り出す（§6.9, §19.7, §20.9, 既存 PHP-A）。
- ORM のモデルを丸ごとシリアライズして返さない。公開用・本人用・管理用で出力の型を分け、返すフィールドを明示的に列挙する（DB に列を足すと API 契約が勝手に広がる構造を避ける）。フィールドの絞り込みはオブジェクト単位の認可の代わりにならない（§19.6, §19.8）。
- 存在を隠す対象の 403 / 404 の使い分けを、同種の対象で一貫させる（404 にしても認可処理は必須）。非公開ファイルは推測困難な名前に頼らず、取得ルートで認可するか、認可後に短期の署名付き URL を発行する。個人向けレスポンスが共有キャッシュに載らないようにする（§6.13, §6.14）。
- 想定する HTTP メソッドと Content-Type だけを受け付ける（非対応は 415）。一覧の limit は上下限で clamp する。バージョンを追加したとき、旧エンドポイントが弱い認可のまま残らないようにする。予約ルートやシステム接頭辞と衝突する ID、下流の処理を壊す値（`"1e+21"` のような数値に見える文字列）を受け付けない（§19.10, §19.11, §19.14, 既存 TS-B）。

誤検知の注意:
- ID を書き換えられること自体は脆弱性ではない。仕様上の公開データなら正当で、問題は認可されない対象に届くこと。公開・本人・他人・管理者のポリシーを先に確かめ、実装されていない仕様を勝手に補って指摘しない（§6.2, §6.4, §6.7）。
- 管理者が全データを読めるかは仕様の判断。共通のポリシー関数があっても呼び忘れは防げないため、すべての入口で呼ばれているかを確認する（§6.10, §6.15）。
- 403 と 404 が混在しているだけでは不備ではない。返していないフィールドの漏えいを書かない（§19.4, §6.18）。

Report only concrete authorization or contract gaps: name the entry point, the object, and the missing check.

## Focus E: 状態と業務ロジック

状態遷移・競合・冪等性・DB 制約・サーバーが決めるべき値・時間と回数・失敗時の倒れ方をレビューする。

- 状態を変える操作は、現在の状態を前提条件にする。許可する遷移を列挙で定義し、遷移元の状態を検索条件か条件付き UPDATE に含める。認可を通っても「今この操作をしてよいか」は別の判定（§20.2, §20.4, §20.6）。
- 確認と更新の間に別のリクエストが割り込む前提で書く（TOCTOU）。条件付き UPDATE の更新件数の確認・行ロック・楽観ロック（version 列）・一意制約のいずれかで競合に耐えるようにする（§20.11）。
- 重複禁止や自己参照禁止などの不変条件は、事前の SELECT だけでなく DB の一意制約・CHECK 制約でも守り、制約違反は握りつぶさずに利用者向けのエラーへ変換する。一つの操作を構成する複数の変更は同じトランザクションに入れる（§20.3, §20.10, §20.15）。
- 再送・二重送信・キューの重複配信で、通知・ポイント・課金・Webhook などの副作用が増えないようにする。副作用は遷移が成功したとき（更新件数が 1 のとき、コミット後）だけ実行する。Idempotency-Key は同じキーで内容が違うリクエストを拒否し、DB の更新と同じトランザクションで記録する（§20.7, §20.8, §29.19）。
- 価格・割引・税・合計・数量上限・所有者・承認者は、クライアントの値（hidden・readonly を含む）を使わず、サーバー側で再計算・決定する（§20.9）。
- 有効期限はサーバーが保存した発行時刻と現在時刻で判定し、クライアントの時刻や hidden の値に任せない。確認画面の内容（宛先・金額）はサーバー側の取引に保存して実行時に照合する。ブロック・削除・在庫・価格などの関連状態は、最終的に変更する直前にも確認する（§20.12, §20.14）。
- 業務上の回数制限（クーポンは一人一回、招待や再設定メールの送信回数）は、通信量のレート制限とは別に、業務キーの一意制約・使用済み状態・時間あたりの上限で守る（§19.12, §20.13）。
- 認可・在庫・外部の確認サービスの失敗や例外を許可側に倒さない（catch の中で許可を返す等）。例外を catch-all で握りつぶさない。途中で失敗したときの再試行の可否と戻し方を設計し、エラー応答でも状態が変わり得る前提で扱う（§20.15, 既存 PHP-B）。

誤検知の注意:
- 自動実行や再申請を仕様として許しているなら、「画面では想定していない」だけで脆弱性にしない。何が禁止された操作なのかを先に確かめる（§20.16）。
- SQLite や単一プロセスのテストで競合が再現しないことは、競合が無い根拠にならない。本番 DB の分離レベル・ロック・制約で判断する（§20.6, §20.11）。
- レート制限が無いことだけで指摘しない。1 リクエストの重さ・課金の有無・業務上の回数制限の有無で判断する（§19.11）。

Report only state, concurrency, or business-rule gaps where a concrete forbidden transition or duplicate effect is reachable.

## Focus F: SSRF と外部 I/O

サーバーからの外部通信、外部 API の応答、上限と timeout、外部入力の構造検証をレビューする。

- サーバーから外部へ通信する機能では、完全な URL を入力させる必要があるかを先に疑う。接続先が有限なら、論理 ID からサーバー側の固定宛先（scheme・host・port・path）へ変換する（§15.10, §15.11）。
- 任意の URL が必要なら、宛先ポリシーを一体で持つ。scheme は必要なものだけにし、userinfo と不要な port を拒否し、host を正規化して完全一致で照合し、名前解決後の IPv4 / IPv6 アドレスでループバック・プライベート・リンクローカル・予約済みを拒否する。URL のパース成功や部分一致を安全の根拠にしない（§15.9, §15.12-15.14, 既存 TS-B）。
- 検証時と接続時で名前解決がずれないよう（DNS rebinding）、検証済みのアドレスへ接続するか、接続レイヤー（ダイヤラーのフック等）で検査する。リダイレクトは新しい宛先なので、自動追従を止めるか、各ホップに同じポリシーと回数上限を適用する（§15.14, §15.15）。
- Sink は HTTP クライアントに限らない。ヘッドレスブラウザ、PDF・画像のレンダラー、フィードや文書のインポーター、XML パーサーの外部取得、SDK の Webhook も含める。Source も、DB に保存された URL・文書内の URL・キュー由来の値を含める（§15.8）。
- 受信したリクエストの Cookie・Authorization・内部ヘッダーを、そのまま外部へ転送しない。秘密はクエリ文字列ではなくヘッダーで渡す（ログや履歴に残るため）。取得結果の本文・内部ヘッダー・詳細な接続エラー・解決済み IP を利用者へ返さない（§15.17, §15.19, 既存 TS-B）。
- 外部 API の応答も信頼できない入力として扱う。TLS 検証を無効化せず、Content-Type とスキーマを検証し、そのまま中継せず自前の型へ変換する（§19.15）。
- 外部 HTTP（connect / read / 全体）・DB クエリ・子プロセス・ジョブに明示的な timeout を持たせる。受信ボディ・フォーム・multipart のパーツ数・外部レスポンスのサイズには、実際に読んだバイト数で上限を掛ける（Content-Length だけを信用しない）。検索の複雑さ・並列数・課金 API の呼び出し回数など、1 リクエストの重さにも上限を設ける（§15.18, §19.11, §24.12-24.14）。
- 外部入力は構文（型・長さ・範囲）と意味（実在・状態）を分けてサーバー側で検証する（クライアント側の検証は UX であって境界ではない）。未指定・空文字・null を区別し、型変換の失敗を既定値で黙って隠さない。未知のフィールドと同名パラメータの複数指定の扱いを契約として決め、検証がすべて通るまで保存や外部送信をしない（§10.3-10.8, §10.16-10.18, 既存 TS-B / PHP-B）。

誤検知の注意:
- HTTP クライアント関数が危険なのではなく、信頼できない値が接続先に届くことが問題。宛先が固定の設定や論理 ID 由来なら指摘しない。ただしリダイレクト追従・本文の返却・ヘッダーの転送は別途確認する（§15.4）。
- timeout やサイズの制限は、内部宛先を許す理由にならない。逆に、クラウドのメタデータ遮断や egress 制限は追加の防御で、アプリ側の検証の代わりにならない（§15.18, §15.20）。
- 入力検証は、SQLi のパラメータ化・XSS の出力処理・認可の代わりにならない。自由文の特殊文字（`<` `'` `&`）を禁止する検証は正当な入力を壊すので、それ自体が指摘対象（§10.9, §10.10）。

Report only concrete paths where an untrusted value controls an outbound destination, or where a missing limit or validation is reachable from external input.

## Focus G: ファイル（アップロード・配信・パス）

ファイルのライフサイクル（受信・検証・変換・保存・配信・更新と削除）と、パスの解決・アーカイブ展開をレビューする。

- 外部入力をファイルパスにしない。取得対象が有限なら、論理 ID や許可リストのマップでサーバー側が実ファイル名を決める。`../` の置換・削除（拒否リスト）を根本対策にしない（§12.5, §12.6）。
- 自前でパスを結合するなら、基準ディレクトリはサーバー設定で固定し、解決後（絶対化・`..` の解消・symlink の解決）の実体が基準の配下にあるかを確認する。親子関係を文字列の前方一致で判定しない（`/srv/files` が `/srv/files-backup` に一致する）。結合ヘルパーが保証する範囲（パス名の逸脱の拒否）と保証しない範囲（symlink・実在・認可）を区別する（§12.8, §12.11, §12.12）。
- 読み取りだけでなく、書き込み・上書き・削除・移動・アーカイブの展開も同じ Sink として扱う。DB に保存された過去の入力（表示名・ファイル名）も Source に含める（§12.4, §12.13）。
- アップロードの許可判断に、accept 属性・元の拡張子・multipart の Content-Type を使わない。本体の内容から判定した形式を許可リストと照合する。必要な形式だけを受け付け、SVG や ZIP など不要な形式のパーサーを動かさない（§11.3, §11.6）。
- 保存名と保存先はサーバーが生成する（ランダムな ID と、検出した形式に対応する拡張子）。元のファイル名は別のメタデータとして持ち、出力時に文脈に応じて処理する。利用者のファイルは、実行権限の無い、アプリのコードや静的配信の外に置く（§11.5, §11.10）。
- リクエストのバイト数・ファイル数・展開後のサイズ（画像のピクセル数）・利用者ごとの Quota・パーサーの CPU とメモリを、それぞれ制限する。画像は完全にデコードしてから再エンコードすると、メタデータや不要な構造を落とせる（§11.7-11.9）。
- 非公開ファイルは、公開用 ID → DB のレコード → 所有者・共有先の認可 → 内部の保存名、の順に引く。署名付き URL は対象・権限・期限を絞る。Content-Type は検証済みの形式からサーバーが決め、nosniff を付け、閲覧が不要なら Content-Disposition: attachment にする。HTML や SVG など能動的な内容を、アプリと同じ Origin で配信しない（§11.11, §11.12, §11.17, §12.14）。
- アーカイブは展開前にエントリ名（`..`・絶対パス・symlink）を検証し、展開後の合計サイズ・ファイル数・入れ子の深さを制限する（ZIP Slip・ZIP bomb）。ファイルの更新は「新規保存 → DB 更新 → コミット後に旧ファイル削除」の順にし、DB の更新に失敗したときの孤立ファイルを片付ける（§11.13, §11.15, §12.16）。

誤検知の注意:
- 基準ディレクトリをサーバー側で固定し、基準と相対パスを別の引数で渡す安全な API を使っていれば、パストラバーサルとしては指摘しない。基準ディレクトリ内で他人のファイルを読めるのはオブジェクト認可の不備なので、分類を分けて報告する（§12.9, §12.14）。
- `..` の文字列検索をレビューの起点にしない。外部入力がファイル操作の Sink に届く経路を見る（§12.4）。
- 「任意のファイルをアップロードできた」と「コードを実行できた」は別。保存先・サーバーの実行設定・到達性を確認した範囲で書く。再エンコードが無いことだけで Must にしない。ランダムな名前の URL は、公開してよいファイル（プロフィール画像等）なら問題ない。Malware 検査の合格は、保存先・認可・XSS の安全を保証しない（§11.7, §11.10, §11.11, §11.16）。

Report only concrete file-handling gaps where an untrusted name, path, type, or size reaches a file Sink, or a private file is served without authorization.

## Focus H: 情報露出・ログ・本番設定

エラー応答・デバッグ機能・秘密の配置・proxy と Host の信頼・セキュリティイベントの記録をレビューする。

- エラー応答に、例外メッセージ・クラス名・スタックトレース・SQL・ファイルパスを返さない。利用者には一般化したコードとリクエスト ID を返し、詳細はサーバーのログへ出す。予期しない例外もハンドラで一般化する。パース・テンプレート・外部通信のエラーも同様（§14.16, §16.20, §21.4-21.6, 既存 PHP-B）。
- デバッグモード・組み込みデバッガ・診断用エンドポイント（プロファイラ等）を公開環境で有効にしない。本番設定は起動時に検査し、欠落や危険な値（DEBUG 有効、短い・既定のシークレット、Cookie の Secure 無効、許可 Host の未設定）なら warning で続行せず起動を失敗させる（§21.7, §24.15）。
- 署名鍵・API キー・DB の認証情報などのシークレットを、ソース・クライアントバンドル（公開用の環境変数を含む）・HTML・ソースマップに入れない。ブラウザへ配るものはすべて公開される（公開キーはプロバイダ側で Origin や quota を制限する）。平文の秘匿値は値オブジェクト等で包み、文字列化やダンプの時点でマスクする（§21.9, §21.10, §24.7, 既存 TS-B / PHP-B）。
- `X-Forwarded-*` / Forwarded は、信頼済み proxy の背後でアプリへの直接経路を閉じたときだけ、信頼する段数か CIDR を指定して使う（無条件に信頼しない）。受信した Host からリセット URL・絶対 URL・リダイレクト先を生成せず、許可 Host か設定値を使う（§24.5, §24.6）。
- 認証の成功・失敗・試行制限、認可の拒否（拒否するすべての経路で同じ方針）、成功した高リスク操作（権限変更・無効化・公開範囲の変更・削除）を、いつ・誰が・何を・結果・理由コード・リクエスト ID が揃った構造で記録する。Web 以外の入口（CLI・ワーカー）も含める（§25.4-25.9）。
- リクエスト・レスポンスの本文やヘッダーを丸ごと記録しない。パスワード・セッション Cookie・Authorization・CSRF トークン・リセットトークン・MFA コードを、ログ・APM・エラー収集へ出さない。相関のために識別子を残すなら、HMAC などで元の値を復元できない形にする（§25.12, §25.13, 既存 PHP-B）。
- クライアントが送る `X-Request-ID` は形式と長さを検証し、不正なら自前で生成し直す。client IP は、proxy の信頼設定を前提に取得する（§25.5, §25.15）。
- 監査やセキュリティイベントの書き込み失敗を理由に、認証・認可を省略しない。監査が必須の操作で記録できなかったときに操作を止めるかどうかを、イベントごとに決める（§25.10, §25.18）。

誤検知の注意:
- ログの不足を認可の回避として報告しない（予防と検知は別の control）。「機密情報が含まれる可能性がある」だけで終わらせず、何が・誰に読めて・どう悪用できるかを書く（§25.23）。
- ソースマップや Server ヘッダーの公開は、それ自体では重大ではない。含まれる内容（秘密・内部エンドポイント）で評価し、内部情報らしい名前だけで削除を求めない（§21.10, §21.11）。
- 構造化ログやシリアライザーは形式の安全化であって、秘密の除外ではない。環境ごとに期待値が違う設定（ローカルの Secure 無効等）を一律に指摘しない（§24.15, §25.11）。
- ログの一般的な品質（コンテキストの付与・ログレベル）は observability 観点の担当。ここではセキュリティに関わる露出と記録だけを見る。

Report only concrete exposure, misconfiguration, or missing security-event paths visible in the diff; state what leaks to whom, or which event is missing.
