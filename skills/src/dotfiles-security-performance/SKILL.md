## 目的

設計・実装で **セキュリティとパフォーマンスを最優先**に判断する。差分に対する詳細なセキュリティレビュー（focus 別の観点・言語別 Sink 表・出力規律）は `review-web-security` が正本で、ここには設計・実装の段階で使う骨格だけを置く。

## 必須チェック（セキュリティ）

脆弱性の名前から入らず、次の3つの問いに戻す（§ は yousukezan『Webアプリケーションセキュリティ入門』の節番号。§29.1）。

- **データ**: 外部入力（DB に保存済みの値・外部 API の応答を含む）が、どこで命令・パス・宛先として解釈されるか。対策は到達先ごとに違う。SQL はバインド、HTML は文脈に応じたエスケープ、コマンドはシェルを避けた引数配列、パスは基準ディレクトリへの固定、URL 取得は宛先の許可リストと名前解決後の検査（§29.2）
- **主体と権限**: 誰が、どの対象に、何をしてよいか。リクエストごとにサーバー側で、オブジェクト単位まで判定する（ログイン済みは許可の根拠にならない）。deny by default / least privilege（§6.1, §6.15）
- **状態**: 現在の状態・許可される遷移・再送・同時実行・回数・時間で規則が破れないか。条件付き更新・一意制約・冪等性で守る（§20.3, §29.4）

あわせて守る原則:

- **秘密情報**: トークン / キー / 個人情報をログ・エラー・レスポンス・クライアントバンドル・コミットに出さない
- **追加の防御と根本対策を混同しない**: CSP・WAF・入力長の制限・コンテナの権限は影響を狭める追加の防御で、連結 SQL や認可の欠落の代わりにならない（§28.10）
- **依存関係**: 新規追加は必要最小限。採否は `dotfiles-plan-first` の Phase 2 で判断する

## 必須チェック（パフォーマンス）

- **I/O**: ループ内の DB/API 呼び出し、N+1 を避ける
- **メモリ**: 余計なコピーやアロケーションを避ける
- **バッチ/ページング**: 大量データは一括読み込みしない
- **計測**: 重要パスは計測/可観測性（ログ/メトリクス/トレース）を意識

## 出力フォーマット

- 重要度を Must / Should / Nice to have に分けて指摘する
