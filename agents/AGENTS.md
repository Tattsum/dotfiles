# AI エージェント共通のグローバル指示

> Claude Code（`~/.claude/CLAUDE.md`）と Codex（`~/.codex/AGENTS.md`）が読む、常時効かせたい原則だけを置く。
> 手順や作業ごとの詳細は該当スキルが正本で、ここには書かない。コマンドの書き方のように機械的に判定できる規則は、dotfiles の `tools/agent-bash-guard`（PreToolUse hook）が理由と直し方を添えて止める。Claude Code だけの指示は `claude/rules/` に置く。

## 原則

### YAGNI 原則

- 「将来こうなるかもしれない」という理由だけで、現時点で呼ばれないコード・到達不能なパス・汎用化を提案しない
- 拡張性の提案は「今のコードで対応できない具体的なユースケースがすでに存在する」場合に限る
- `interface` の追加・`switch` の汎化・抽象クラスの導入などは、その必要性を具体的な根拠とともに示せない限り提案しない

### 情報配置の四分割原則

実装・レビュー・コミットのすべてで、4 種類の情報をそれぞれ正しい置き場所に書き分ける。片方に書くべき情報を他方に書かない。

| 置き場所 | 書くこと | 書いてはいけないこと |
|----------|----------|----------------------|
| **コード** | **How**（どう実現するか）。処理そのもの・制御フロー・アルゴリズムをコード自体で表現する | — |
| **テストコード** | **What**（何を満たすか）。仕様・期待される振る舞い・契約をテスト名とテーブル駆動ケースで表現する | 実装の How の丸写し |
| **コミットログ** | **Why**（なぜこの変更が必要か）。変更の理由・背景・課題を残す | What（差分を読めば分かる「何をしたか」の羅列） |
| **コードコメント** | **Why not**（なぜ他の手を採らなかったか）。却下した代替案・トレードオフ・落とし穴・「一見こうしたくなるがしてはいけない」制約 | What / How（コードと命名で表現できる説明） |

判断の指針:

- コード = How: 「何をするか」はコメントで説明せず、関数名・変数名・型で表現する（`u` でなく `user`、`tmp` でなく `pendingOrders`）。処理内容をなぞるコメントは書かない
- テスト = What: 仕様・振る舞いはテスト名・テーブル駆動のケースで表現し、コメントで補わない。テストが仕様書として機能する状態にする
- コミットログ = Why: 変更の理由はコミットメッセージの Reason（`dotfiles-commit-push` の規約）に書く。「なぜこの変更が要るのか」をコメントやコードに埋め込まない
- コメント = Why not: コードコメントは本当に必要な場合に限定し、デフォルトは書かない。書くのは「なぜ別の（一見自然な）選択肢を採らなかったか」＝トレードオフ・制約・却下した代替案・ハマりどころに限る。単なる背景説明や「なぜこうするか」の順方向の理由はコミットログへ寄せる。Why not は 1 行に収める（2 行以上要るなら、コミットログか設計文書に書く内容が混ざっている。godoc・PHPDoc など言語規約の doc コメントは対象外）

レビュー時も、この四分割に反するもの（コメントに How/What を書く、コミットログに What だけを並べる、テストで表現すべき仕様をコメントで補う、命名・テスト・型で代替できる説明的コメント）は指摘対象とする。

## 作業の基本

- 呼び出し元ごとの準備や個別の例外を増やす前に、既存の責務・情報の正本・共有契約・配置慣例を確認する。共通の不変条件が経路によって抜けないかを見る。詳細な確認観点は `dotfiles-code-review` の「横断チェック」を参照する
- リポジトリのドキュメント（README やその repo の CLAUDE.md・AGENTS.md など）と既存のコードが食い違うときは、既存のコードの規約に従い、見つけた食い違いを最後の返答ですべて挙げる
- 仕様や挙動が曖昧なときは、記憶で答えずに公式ドキュメント・公式リポジトリを先に当たる
- 挙動・等価性・「無い」ことを断定する前に、一次情報で確かめる。確かめられなければ断定せず「未確認」と書く
  - 挙動: 呼び出し経路を画面・API・ガードまで辿る。到達しない分岐は「安全弁」と書いて区別する
  - 等価性: `git show <base>:<path>` で元の実装を読み、キー・値・件数まで照合する。自分で書いたノート・テスト・fake との一致は証拠にしない（循環する）。一致しなければ、テストの抜けでなく挙動の変更として扱う
  - 不在: 言い回し（日本語の表現を含む）、既定以外のブランチ、関連する台帳や issue まで探し、見つからなければ探した範囲を書く
  - 特定のページや顧客で再現するバグは、机上で調べる前に現物（URL・DOM・保存データ）を取る
  - 先例は件数でなく、機構が同じ実例だけを引く。見つからなければ「先例では決められない」と書く
- コードを変えたら、完了を報告する前に `dotfiles-lint-and-test`（PHP は `dotfiles-php-laravel-lint-test`）スキルで lint / format / test を通す
- 共有の挙動・契約を変えたら、それを真似ている fake・stub をリポジトリ全体から `rg` で洗い出してまとめて直す。push 後は、絞ったテストでなく CI 全件（`gh pr checks`）が通ったのを見てから完了と報告する（PR 本文の「green」も同じ）。pending の間は完了と書かず（待つなら `gh pr checks --watch`）、落ちたら直して見直す。CI が無ければ無いと書く
- 本番に痕跡が残る追加検証や対照実験を提案する前に、既存のデータで代替できないか、その結果で結論が変わるかを詰める。既存のデータで決着しなかったときに、理由を添えて提案する
- 本番や本番相当の環境のデータで検証するときは、始める前に、実在する宛先（メール・SMS・Webhook・招待）へ通知が届かないことを確かめる。終わったら自分が作ったデータ（検証用アカウントを含む）を削除し、アカウントならログインできなくなったことまで確かめて完了とする。削除や確認ができないときは完了と書かず、残っているデータと削除の手順を利用者に渡す
- GitHub に日本語の文章（PR 本文・Issue・コメント・返信）を出す前に `natural-japanese` スキルの手順で `--genre tech` の lint と `--reading-load` を回す。プロジェクトの外の読み手に通じない略語（社内やリポジトリ独自の略称）は使わず、一読で通じる語にする。言い換えの語は新しく作らず、そのリポジトリの既存の語彙を探して使い、専門語が要るなら初出で 1 回だけ説明する。言い換えたあと、元の文が表していた対比が残っているかを読み返す

## スクリプトの言語

新しく書くスクリプトや小さなツール（一時ディレクトリの使い捨て・調査用のヘルパー・新しい CLI）は、言語の指定がなければ Go で書く。既存のスクリプトは別の言語に書き換えず、今の言語のまま編集する。アプリ本体のコードはその repo の言語で書く。

- 使い捨ての Go は標準ライブラリだけで書き、go.mod を持つ repo の外（一時ディレクトリなど）に置いて `go run <file>.go` で動かす。外部モジュールが要るなら、使い捨てでなく go.mod を持つツールとして作る
- Rust を選ぶのは、利用者が指定したとき・既存の Rust プロジェクト・性能や型の表現が本質の処理に限る（2026-10 時点の stable の cargo では単一ファイル実行の cargo script が使えないので、既定にしない）
- Python・Node・Ruby・Perl は、新しく書くときには選ばない。既存スクリプトの実行と編集はよい
- 次に当たるときは既定より優先する（上ほど強い）
  1. 利用者が言語を指定したとき
  2. スキルが言語や手段を決めているとき（jq で集計する・同梱の Python を使う など）
  3. 既存ファイルの編集、または Go を受け付けない言語の規約や CI がある repo では、それに従う
  4. CLI をパイプでつないだり for で繰り返し呼んだりするだけの処理や、jq・rg で済むワンライナーはシェルで書く。JSON の加工・集計や、データを見て分岐する処理が入るなら Go で書く
